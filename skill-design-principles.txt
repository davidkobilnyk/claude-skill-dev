1. Be concise — the context window is a shared resource. Only the name/description preload into every conversation; the full body loads only when triggered, but once loaded it competes with everything else in context. Assume Claude already knows general concepts (what pdfplumber is, what an API is) and only write down what's specific to your workflow. A 50-token version that skips explaining "what is a PDF" beats a 150-token version that doesn't.
2. Match degrees of freedom to task fragility. For open-ended judgment calls (code review), give high-freedom text guidance and trust Claude's reasoning. For fragile, error-prone, or must-be-exact operations (a DB migration script), give low-freedom, exact commands with no room to improvise. Anthropic's own framing: a narrow bridge over a cliff needs guardrails; an open field needs only general direction.
3. Use progressive disclosure. SKILL.md is the table of contents, not the whole manual — push detail into linked reference files that Claude reads only as needed. Keep the body under ~500 lines. Split by domain (finance.md, sales.md) so unrelated context never loads. Keep references one level deep from SKILL.md — nested reference chains cause Claude to partially skim rather than fully read.
4. Write descriptions for discovery, in third person, with concrete triggers. The description is what Claude uses to decide whether to load the skill at all (often choosing among 100+ skills), so it needs both what it does and when to use it, with specific keywords — not "helps with documents" but "extracts text and tables from PDFs... use when the user mentions PDFs, forms, or document extraction."
5. Keep terminology and structure consistent. Pick one term (e.g., always "field," never mixing "field/box/control") and stick to it — inconsistency makes instructions harder for Claude to parse reliably.
6. Avoid time-sensitive claims. Don't write "before/after [date], use X" — describe the current method as current, and park deprecated approaches in a clearly labeled "old patterns" section so the skill doesn't silently go stale.
7. Build workflows and feedback loops for complex or quality-critical tasks. Sequential checklists prevent step-skipping; a validate→fix→repeat loop (with a validator, whether a script or a checklist) meaningfully improves output quality on multistep work.
8. For scripts: solve, don't defer. Handle errors explicitly in bundled code rather than letting failures fall back on Claude to improvise, and justify any constants (no "voodoo" magic numbers) so Claude — or a future editor — knows why a value was chosen.
9. Build evaluations before writing extensive docs, and iterate against real usage. Anthropic's evaluation-driven approach: run Claude without the skill, document the actual gaps, write minimal instructions targeting those gaps, then test with a second Claude instance and refine based on where it stumbles — not based on anticipated needs. This lines up closely with your own pipeline's test-before-build principle.
